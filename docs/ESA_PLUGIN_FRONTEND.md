# ESA Redmine frontend

The English plugin follows Redmine's native layout and permissions. The ESA menu lists manually forwarded issues visible to the logged-in user, with filters, sorting and pagination. The former category/tag routing controls and Agent classification reports have been removed. When explicitly enabled, an optional ticket detail panel offers local label suggestions and human correction; it does not change forwarding or engineering routing. See [classifier operations](CLASSIFIER.md).

The link on an ordinary issue opens its ESA page even before forwarding. **Forward to ESA** submits the current snapshot through the durable outbox. The optional force choice creates a fresh diagnosis and may spend again. Only this action forwards an issue; new/edit hooks do not.

Upload accepts UTF-8 JSON/CSV, previews rows and creates Redmine issues while preserving original uploads and source-key deduplication. Import does not forward or analyze them. Metadata saves component/version/environment and resolution information locally; forward the issue separately to submit an updated snapshot.

The ticket page keeps the status panel, manual forwarding and metadata form. Status refreshes automatically (every 3 seconds while processing, every 15 seconds while idle), pauses in hidden tabs, and backs off after network failures. It replaces only the status fragment so unsaved metadata edits survive. Manual forwarding waiting in the outbox is shown as Queued before the backend receives it.

Once a result is available, **View ESA report** opens a separate authenticated report page with recommendations, code findings, evidence, usage, advisory alerts, history and engineer review controls. The same project, issue visibility and private-issue restrictions apply to the page and status endpoint.

**Fill metadata from ESA** copies the current resolution reason, cause, solution and validation suggestions into the local form, with **Undo fill** available. It leaves technical-context fields unchanged and neither saves nor forwards. Engineer-reviewed resolution text takes precedence; Agent causes/repairs and planned verification are explicitly labeled unverified/not applied/not performed. Failed, active, withdrawn or rejected advice cannot be used for filling. A fill link on the report returns to the ticket form. The suggestion endpoint requires Submit ESA permission, returns only the resolution values, and makes no Agent calls.

Browser polling uses `/esa/tickets/:id/status` and filling uses `/esa/tickets/:id/metadata_suggestion`, both with the normal Redmine session and `Accept: application/json`. Keep these URLs extensionless: Redmine treats a `.json` URL as an API request and does not use the browser session in the same way. The full report is `/esa/tickets/:id/report`; none of these browser routes requires exposing an ESA service token.

The report shows intake provenance, processing state, missing information, recommendations, concrete code findings, evidence, usage, advisory alerts and review controls. A forwarded closed issue becomes a case draft. Case/report approval does not close the Redmine issue.

Every forwarded open issue goes to Routing Agent, which retrieves local Issue records and decides whether to reuse an Agent analysis or engineer solution, join a matching `investigating` task, request information, or queue engineering. The English `Investigating` state is filterable and covers capacity waiting, analysis and assignment routing; at most three engineering workers run concurrently. Reuse invokes no engineering Agent. Accidental non-engineering forwarding can show **Returned To Support**, with the Routing Agent's service advice and zero engineering calls. A new investigation shows **Unassigned until analysis completes**. Intake does not create an Engineering Issue. After reuse, the service links the selected Issue. After supported analysis, Engineering Agent submits a grouping request and Routing Agent decides existing/new membership before backend validation. The separate report page shows the request, final routing decision and separate stage call counts. Its membership review controls appear once an Issue has been assigned.

View ESA, Submit ESA and Review ESA permissions remain required; import also requires Add issues. Issue visibility can be narrower than project visibility, and private issues are excluded from shared pages. The service token never enters browser requests. The prototype limits authorized scopes to 2,000 visible ESA issues.

The forwarding-column migration is required for the new outbox. Old automatic events remain stored but are not delivered. See [manual forwarding](MANUAL_FORWARDING.md).
